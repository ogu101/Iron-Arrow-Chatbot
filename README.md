# Iron Arrow History Chatbot

A conversational AI built on [Chainlit](https://chainlit.io) and the [Anthropic API](https://docs.anthropic.com) that answers questions about the history of Iron Arrow Honor Society at the University of Miami.

The chatbot uses a **progressive disclosure RAG** architecture: rather than retrieving one flat chunk per query, it retrieves context in up to three layers of increasing depth, stopping as soon as it has enough information to answer. This keeps token usage low for general questions while still supporting granular, detail-level queries.

---

## How it works

### The four layers

Every section of the Iron Arrow history PDF is preprocessed into a JSON chunk with four layers. Each layer is a different depth of representation of the same source material.

| Layer | When used | What it contains | How it's generated |
|---|---|---|---|
| **Layer 0 — Index** | Always in context | Section name, one-sentence summary, subsection list | Built at startup from section metadata |
| **Layer 1 — Overview** | 1st tool call for a section | Thematic paragraph + 5 narrative bullets | Claude-generated during preprocessing |
| **Layer 2 — Details** | 2nd tool call for a section | Subsection-by-subsection fact bullets with names, dates, and key events | Claude-generated during preprocessing |
| **Layer 3 — Full Text** | 3rd tool call for a section | Complete raw text extracted from the split PDF | Extracted live from disk at query time |

Layer 0 is embedded directly in the system prompt, so the model always knows what sections exist without making any tool calls. Layers 1 and 2 are stored in JSON chunk files. Layer 3 is intentionally **not** stored in JSON — it is extracted live from the split PDF to keep chunk files lightweight.

### The retrieval state machine

Each conversation session maintains a `retrieval_state` dictionary that tracks how many times each section has been retrieved:

```
retrieval_state = {}   # initialized empty at conversation start

First  call for a section key → returns Layer 1 (overview)
Second call for the same key  → returns Layer 2 (details)
Third  call for the same key  → returns Layer 3 (full text)
Further calls                 → "already at maximum depth"
```

The model never chooses a layer directly — it calls the same `retrieve_context(section_key)` tool repeatedly, and the state machine determines what to return. This enforces the protocol: the model must always see Layer 1 before Layer 2, and Layer 2 before Layer 3. `retrieval_state` persists across turns, so if a section has already been retrieved to depth 2 earlier in the conversation, the next call for it will go straight to Layer 3.

### The agentic loop

When a user sends a message, `app.py` enters a `while True` loop:

1. Call the Anthropic API with the full conversation history and tool definition
2. If the response contains tool calls → run `execute_retrieve_context`, append results to message history, loop back
3. If the response contains no tool calls → send the final answer to the user and break

The loop continues until the model decides it has enough context to write a complete answer.

## Setup

### 1. Install dependencies

```bash
pip install -r requirements.txt
```

`requirements.txt` should contain:

```
chainlit>=1.1.301
anthropic>=0.29.0
pypdf>=4.0.0
pandas>=2.1.0
python-dotenv>=1.0.0
openpyxl>=3.1.2
```

### 2. Create a `.env` file

```
ANTHROPIC_API_KEY=sk-ant-...
CHUNKS_DIR=./chunks
SECTIONS_DIR=./sections
```

### 3. Verify `config.py` loads the environment

`config.py` must call `load_dotenv()` and read from environment variables:

```python
from dotenv import load_dotenv
import os

load_dotenv()

ANTHROPIC_API_KEY = os.getenv("ANTHROPIC_API_KEY")
CLAUDE_MODEL      = "claude-sonnet-4-6"
# ...
```

## Preprocessing (run once)

Before starting the chatbot, run `split_pdf.py` to split the source PDF and generate the JSON chunks. This script makes two Claude API calls per section (to generate Layers 1 and 2) and will take a few minutes to complete.

```bash
python split_pdf.py \
  --input    "iron-arrow-history.pdf" \
  --output_dir ./sections \
  --chunks_dir ./chunks \
  --xlsx     ./resources.xlsx
```

**Arguments:**

| Argument | Default | Description |
|---|---|---|
| `--input` | *(required)* | Path to the source PDF |
| `--output_dir` | `./sections` | Where to write the split section PDFs |
| `--chunks_dir` | `./chunks` | Where to write the JSON chunk files |
| `--xlsx` | `./resources.xlsx` | Path for the metadata spreadsheet output |

**Outputs:**

- `sections/` — 9 split PDFs, one per section (e.g. `section_01_beginnings.pdf`)
- `chunks/` — 9 JSON chunk files, one per section (e.g. `section_01_beginnings.json`)
- `resources.xlsx` — metadata table with section keys, names, descriptions, page ranges, and word counts

> **Note:** Page boundaries in `SECTIONS` at the top of `split_pdf.py` are 0-indexed and were set for a specific edition of the Iron Arrow history PDF. If you are using a different file, open each split PDF after running and verify the boundaries are correct before using the chatbot.

## JSON chunk format

Each file in `chunks/` has this structure:

```json
{
  "layer0_index": {
    "key":                  "section_01_beginnings",
    "section_num":          1,
    "name":                 "Section One: The Beginnings",
    "description":          "Origins of Iron Arrow: Osceola, Bowman Foster Ashe...",
    "subsections":          ["Osceola", "Bowman Foster Ashe", "..."],
    "source_pdf":           "iron-arrow-history.pdf",
    "start_page":           6,
    "end_page":             28,
    "one_sentence_summary": "Section One: The Beginnings: Origins of Iron Arrow..."
  },
  "layer1_summary": {
    "paragraph": "Iron Arrow was founded in 1926...",
    "bullets": [
      "Osceola serves as the symbolic figurehead...",
      "Bowman Foster Ashe conceived the society...",
      "..."
    ]
  },
  "layer2_details": {
    "text": "OSCEOLA\n- Seminole warrior whose name means...\n\nBOWMAN FOSTER ASHE\n- Born 1885..."
  }
}
```

Layer 3 (full text) is not stored in the JSON. It is extracted at query time from `sections/<key>.pdf` using `pypdf`.

## Configuration reference (`config.py`)

| Variable | Description |
|---|---|
| `ANTHROPIC_API_KEY` | Anthropic API key, loaded from `.env` |
| `CLAUDE_MODEL` | Model string, e.g. `claude-sonnet-4-6` |
| `MAX_TOKENS_PER_CONVERSATION` | Total token budget per session before the chatbot stops responding |
| `MAX_TOKENS_PER_REQUEST` | `max_tokens` passed to each individual API call |
| `CLAUDE_TEMPERATURE` | Sampling temperature (recommend `0` for factual retrieval) |
| `WELCOME_MESSAGE` | Message sent to the user at the start of every session |
| `ERROR_MESSAGES` | Dict of error strings keyed by type: `token_limit`, `rate_limit`, `api_key`, `timeout`, `generic` |
| `LOG_LEVEL` | Python logging level, e.g. `INFO` or `DEBUG` |
| `LOG_DIR` | Directory for log files, e.g. `./logs` |
| `LOG_FORMAT` | Python logging format string |
| `LOG_DATE_FORMAT` | Python logging date format string |

## Common errors

**`ModuleNotFoundError: No module named 'chainlit'`**
Run `pip install -r requirements.txt`.

**`AuthenticationError`**
The `ANTHROPIC_API_KEY` in `.env` is missing, misspelled, or not being loaded. Confirm `config.py` calls `load_dotenv()` before reading environment variables.

**`(No sections loaded — run split_pdf.py first.)`**
The `chunks/` directory is empty or the `CHUNKS_DIR` path in `.env` is wrong. Run `split_pdf.py` first, then verify the path matches where the JSON files were written.

**`Port already in use`**
Another process is using port 8000. Run `chainlit run app.py --port 8001`.

**`Full text unavailable: split PDF not found and no JSON fallback`**
The `sections/` directory is missing or `SECTIONS_DIR` in `.env` points to the wrong location. Layer 3 retrieval reads directly from the split PDFs on disk.

## Limitations

- **Scope is bounded by the source PDF.** The third edition of the Iron Arrow history covers events up to approximately 1976 in narrative depth. Questions about post-1976 developments — the 2018 MOU with the Miccosukee Tribe, current membership statistics, contemporary cultural sensitivity positions — are outside the document's scope. The chatbot will say so rather than hallucinating.
- **Section routing relies on semantic reasoning, not vector search.** The model routes to sections by reading Layer 0 index entries in the system prompt and reasoning about which section likely contains the answer. For vague or cross-cutting questions this is reliable; for questions whose topic isn't signaled by any section or subsection name, it may miss the right section or need to retrieve multiple sections.
- **`retrieval_state` resets per conversation.** Each new chat session starts with all sections at depth 0. There is no cross-session memory of which sections have been retrieved.
